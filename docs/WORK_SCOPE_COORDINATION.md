# 여러 MCP의 Revit 작업 범위 배정과 충돌 확인

## 적용 조건 — 현재 실행 중인 호스트 기준

**예약은 모든 플러그인에서 무조건 요구하는 규칙이 아니다.** 새 TypeScript 서버의
도구 목록에 `revit_work_scope`가 보여도, 실제 로드된 Revit 호스트가 구버전이면
그 명령을 처리할 수 없다. 소스 코드의 구현 여부와 설치·실행 상태를 구분한다.

| 확인한 상태 | 작업 방식 |
|---|---|
| `status`에서 `supported=false`, 또는 정확한 `Unknown command: 'work_scope'` 응답 | 이미 승인된 작업은 기존 도구로 진행. 미지원만을 이유로 예외 승인을 다시 묻지 않음 |
| 지원하지만 `coordination_enabled=false` | 기존 단독 수정 방식 가능. 여러 작업자의 예약 분담을 시작하려면 acquire로 조율 모드 활성화 |
| 지원하고 `coordination_enabled=true` | 예약 규칙 준수. 범위·만료·변경 충돌을 해결한 뒤 수정 |
| 연결/타깃/레지스트리 오류, 충돌·만료·stale, 지원 여부 불명 | 미지원으로 간주하지 않고 실제 오류를 해결. 보호 장치 우회·자동 해제 금지 |

`revit_ping`에 `work_scope_supported`가 없다는 사실만으로 미지원이라고 단정하지
않는다. 필요한 경우 `revit_work_scope op=status`를 한 번 호출해 확인한다. 같은
실행 세션에서 이미 확인한 미지원 응답은 재사용할 수 있다. 이번 호환성 수정 이후
MCP는 구버전의 정확한 unknown-command 응답을 status의 `supported=false`,
`reservation_required=false`로 설명한다. acquire는 예약을 만든 것처럼 성공시키지
않고 `WORK_SCOPE_UNSUPPORTED`를 반환한다.

기존 방식에서는 모델 수정 담당을 한 명으로 두고, 문서/세션을 고정한 뒤 현재
파라미터 재조회 → 승인된 기준으로 적용 → 사후 검증을 수행한다. 기존 승인된
파라미터·적용 기준·범위를 그대로 사용하며, 선택적인 예약 기능의 미지원만으로
작업을 중단하거나 같은 승인을 다시 요청하지 않는다. 실제 범위가 달라졌다면 그
변경은 별도로 판단한다. 기존 방식에 예약·충돌 보호가 적용됐다고 보고하지 않는다.

아래 예약 절차와 제한은 **지원되는 조율 기능을 사용하는 경우**에 적용한다.

## 검토 결과와 구현 범위

서로 다른 Codex/MCP 프로세스가 같은 Revit 모델을 작업할 때, 작업 범위는
Revit 호스트의 공용 레지스트리에서 관리한다. TypeScript 서버마다 별도 잠금을
두면 다른 MCP 연결을 막을 수 없으므로 호스트의 기존 쓰기 게이트 안에서 검사한다.
Revit API 실행은 계속 순차 처리하며, 분석·계획 및 서로 겹치지 않는 담당 범위는
여러 에이전트가 동시에 유지할 수 있다.

| 범위 | 배정 방식 | 허용되는 변경 |
|---|---|---|
| `elements` | 호스트 요소 ID 1–5000개, 다른 예약과 정확한 ID 중복 금지 | 기본 제공 인스턴스 Comments/Mark의 단건·배치 변경 |
| `document` | 문서 전체 독점, 다른 활성 예약과 공존 불가 | 기존 생성·형상·타입·삭제·스크립트·뷰·내보내기 명령 |

층/구역/카테고리 이름은 예약 키가 아니다. 먼저 조회로 **현재 호스트 ID**를
수집하고, 예약한 뒤 편집 계산에 사용할 데이터를 다시 조회한다. 이름/조건 기반
예약은 요소가 다른 층으로 이동하거나 필터에 새로 들어오는 경우 보호 범위가
달라지므로 이번 구현에서는 사용하지 않는다. 링크 요소는 호스트 요소와 ID가
겹칠 수 있어 예약 입력으로 쓰지 않는다. 큰 64비트 ID는 십진수 문자열로 전달한다.

`elements`의 허용 범위를 좁힌 이유는 이동·삭제·타입 변경이 호스트, 종속 요소,
다른 인스턴스에 영향을 줄 수 있기 때문이다. 사용자 지정 문자열 파라미터도
업데이터 등의 동작을 추론할 수 없으므로 문서 전체 예약이 필요하다.
이름이 중복된 파라미터는 좁은 범위에서 수정하지 않는다.

## 사용 순서

각 Codex는 **별도 TypeScript MCP 서버 프로세스**를 사용한다. 같은 MCP 서버를
공유하는 하위 에이전트들은 하나의 소유자로 취급되므로 별도 예약 분담에 쓰지 않는다.

1. `revit_list_sessions`와 `revit_set_target`으로 정확한 Revit/문서를 지정한다.
2. `revit_work_scope`의 `op=status`로 실제 지원 여부와 배정 현황을 확인한다.
   미지원이 확인되면 위 적용 조건에 따라 기존 방식을 사용한다.
3. 범위를 예약한다. 아래 ID는 설명용이며 라이브 모델에서 다시 조회해야 한다.

   ```json
   {"op":"acquire","scope":"elements","element_ids":[123,456],"label":"A: 벽체 주석 정리","ttl_seconds":300,"idempotency_key":"task-a-reserve-001"}
   ```

4. 예약 성공 후 해당 요소를 다시 조회하고, 기존 수정 도구를 사용한다. 예:

   ```json
   {"element_ids":[123,456],"parameters":{"Comments":"검토 완료"},"idempotency_key":"task-a-write-001"}
   ```

   파라미터 이름은 현재 Revit 언어/프로젝트에서 조회한 실제 이름을 쓴다.
   MCP 서버가 예약 토큰을 기존 명령에 자동으로 첨부한다.
5. 긴 작업은 `{"op":"renew","ttl_seconds":300}`으로 갱신한다.
6. 끝나면 `{"op":"release"}`를 호출한다.

새 요소 생성 등에는 `scope=document`를 사용하고 `element_ids`는 생략한다.
문서 전체 작업을 시작하기 전에 모든 요소 예약을 해제하거나 만료시켜야 한다.
겹치는 예약 요청은 즉시 실패하며, 예약 대기열이나 자동 재시도는 만들지 않는다.
모든 활성 예약을 해제한 뒤 문서 예약을 확보한 담당자가 작업하고 해제하면 된다.

## 보호 규칙과 복구

- 최초 예약이 성공하면 그 문서는 **조율 모드가 유지**된다. 마지막 예약의 해제나
  만료가 예약 없는 쓰기를 허용하지 않는다. 기존 MCP/직접 WebSocket 연결도 검사한다.
- 일반 조회는 예약 없이 가능하다. `execute_script`의 query 모드, 벽 높이 명령의
  dry-run, UI 조작, 내보내기는 보수적으로 문서 전체 예약을 요구한다.
- 예약은 기본 300초, 30–1800초다. MCP 종료/연결 끊김 시 즉시 풀지 않고 만료를
  기다린다. 같은 MCP 프로세스의 재연결은 토큰을 유지한다. 프로세스 재시작은 새 소유자다.
- Revit의 `DocumentChanged`에서 생성·수정·삭제 ID를 받아 예약 대상과 해당 요소의
  타입/레벨 변경을 감지한다. 문서 전체 예약은 문서의 모든 트랜잭션 변경을 감지한다.
  성공한 자기 명령은 자기 예약의 기준 상태를 갱신한다. 실패한 명령은 이를 지우지 않는다.
  Autodesk는 이 이벤트가 커밋·Undo·Redo 때 발생한다고 명시한다.
  [Autodesk API 문서](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/988dd6cf-fcaa-85d2-622d-c50f13917a13.htm)
- 만료/충돌 검사는 쓰기 게이트를 기다린 **뒤**, 명령 실행 직전에 한다.
- `WORK_SCOPE_STALE`: 예약 해제 → 새 키로 재예약 → 현재 데이터 재조회 → 수정 재계산.
  갱신(`renew`)은 변경 사실을 확인한 것으로 취급하지 않는다.
- `WORK_SCOPE_OUTSIDE`: 범위 안의 요소만 수정하거나, 요소 예약을 모두 정리한 뒤
  문서 전체 예약을 사용한다. 배치 일부가 범위 밖이면 실행 전 전체 명령을 차단한다.
- `WORK_SCOPE_EXPIRED`: 새 키로 예약하고 다시 조회한다. 오래된 acquire 요청을
  재전송해도 해제/만료된 예약은 되살아나지 않는다.
- `WORK_SCOPE_CONFLICT`: status에서 담당 작업을 보고 ID를 나누거나 해제를 기다린다.
- `WORK_SCOPE_TRACKING_FAILED`: 변경 추적 근거를 잃었으므로 쓰기를 차단한다.
  작업을 보존하고 해당 Revit 프로세스를 재시작해 복구한다.
- 단독 작업 방식으로 돌아갈 때는 문서 전체 예약을 확보한 소유자가
  `{"op":"disable"}`을 호출한다. 모델 자체를 수정하지 않으며 자기 예약도 해제한다.
- 다른 이름으로 저장하면 라우팅 fingerprint를 다시 확인해야 하지만 같은 열린
  문서의 조율 모드는 유지된다. status가 반환한 자기 토큰을 `lease_token`에 넣어
  이전 예약을 해제할 수 있다.
- 반복된 모델 변경 명령은 기존 멱등성 캐시를 사용한다. 소유자별 키 공간과
  예약 토큰을 함께 확인한다. 캐시 재응답은 모델을 재실행하지 않는다.

활성 예약은 문서당 최대 50개, acquire 이력은 문서당 호스트 수명 동안 1000개다.
이력을 보존해 오래된 재시도가 예약을 되살리지 않도록 한다. status는 최대 50개
예약과 예약당 20개 ID 미리보기를 반환하며, 다른 소유자의 토큰은 공개하지 않는다.

## 보장하지 않는 것

이 기능은 협력하는 MCP들의 충돌을 줄이는 장치다. Revit Worksharing의 요소
소유권, 중앙 모델 동기화, 보안 격리 또는 임의의 종속관계 분석을 대신하지 않는다.
사용자나 다른 Add-in의 편집을 잠그거나 되돌리지 않는다. 다른 작업자가 실제로
변경한 보호 대상은 다음 MCP 쓰기에서 감지한다. 트랜잭션을 만들지 않는 사용자
선택·활성 뷰 변경, 외부 파일, 다른 Revit 프로세스의 중앙 모델 변경은 이 예약으로
완전히 보호되지 않는다. 선택/뷰에 의존하는 명령은 실행 직전에 대상을 확인한다.

에이전트가 조회 결과의 의미를 제대로 이해했는지, 예약 전 데이터를 재사용하는지까지
자동 판별하지 않는다. 작업 계획의 자동 분배나 공정한 FIFO 예약 스케줄러도 포함하지 않는다.
향후 형상 명령을 요소 범위에 허용하려면 명령별 실제 영향 요소와 종속관계를 먼저 검증한다.

## 설치와 검증

호스트 WebSocket/이벤트 처리 변경이므로 **CommandSet hot reload만으로 적용되지 않는다**.
새 호스트 DLL 배포 후 해당 Revit을 재시작하고, 새 TypeScript 서버를 사용하도록 MCP
세션도 다시 시작한다. `revit_ping`의 `work_scope_supported=true`로 호스트 지원을 확인한다.
이번 개발에서는 라이브 모델 변경이나 실행 중 Revit의 강제 종료를 수행하지 않았다.

자동 검증:

```powershell
npm run build
npm run test:unit
dotnet run --project tests/WorkScopeSmoke -c Release
dotnet build plugin/RevitMCPPlugin/RevitMCPPlugin.csproj -c Release -f net48
dotnet build plugin/RevitMCPPlugin/RevitMCPPlugin.csproj -c Release -f net8.0-windows '-p:REVIT_2025_PATH=C:/Program Files/Autodesk/Revit 2025'
```

정책 테스트는 실제 레지스트리/검사 코드를 Revit API 테스트 대역과 실행한다.
TypeScript 테스트는 실제 로컬 WebSocket으로 두 MCP 소유자 격리, 동시 acquire/write/release,
오류 후 토큰 유지 및 대상 문서 변경 차단을 확인한다. 이는 라이브 Revit 검증의 대체가 아니다.

설치 후 별도 시험 모델에서 확인할 항목: 두 Codex의 겹치는 예약 거부, 분리된 ID의
주석 배치 변경, 타입/형상 작업의 문서 예약 요구, UI 수동 수정·Undo 후 stale 차단,
대기 중 TTL 만료, 저장/문서 전환/재연결, 단독 모드 복귀다.

### 2026-09-11 호환성 규칙 수정

새 도구 목록/문서가 먼저 배포되고 실행 중인 호스트에는 예약 기능이 없어,
에이전트가 승인된 기존 작업을 불필요하게 중단하는 문제가 확인됐다. 적용 규칙을
호스트 지원 여부와 조율 활성 상태에 따라 구분하고, 미지원 상태 안내를 추가했다.
예약 충돌·만료·연결 실패는 미지원으로 변환하지 않으며, 이미 보유한 예약 토큰도
자동 제거하지 않는다. 기존 프로젝트 작업 기록과 실제 적용 기준은 변경하지 않았다.

검증: TypeScript 전체 빌드와 공용 코어·Revit·AutoCAD 테스트 80개가 통과했다.
새 MCP 프로세스를 통해 실행 중인 호스트의 status를 읽기 전용으로 확인했고,
`supported=false`, `coordination_enabled=false`, `reservation_required=false`가
반환됐다. 모델 수정이나 Revit 재시작 없이 호환 안내가 동작했다. 이미 실행 중인
MCP 프로세스는 새 응답/도구 설명을 받으려면 다시 연결해야 하지만, 기존의 정확한
unknown-command 응답만으로도 위 수정된 작업 규칙을 적용할 수 있다.
